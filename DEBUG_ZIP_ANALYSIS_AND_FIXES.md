# Arya Debug ZIP — line-by-line analysis and the fixes applied

**Debug bundle:** `arya-debug-20260830_162929.zip`
**Device:** Huawei ADY‑LX9 (Kirin 9000S), Android 12 (SDK 31), 12 GB RAM, 4.6 GB free at report time.
**App:** `io.agents.arya` v1.2.20 (125), release build (not debug), `:engine` = separate process.

This document explains **what every file/line in the bundle means**, identifies the **root causes**,
and shows the **code changes already applied** to the repo so the app actually works.

---

## 1. What the bundle is

A bug‑report ZIP generated by Arya's own diagnostics (`EngineLog`). It contains a summary, crash/process
dumps, logcat, and the native engine's diagnostic trace files. Nothing in it is encrypted or obfuscated —
these are plain logs.

| File | What it is | Conclusion |
|------|-----------|-----------|
| `summary.txt` | One‑page health report assembled by the app | The single most useful file. Confirms local mode, CPU‑only, model path, RAM, and the last engine death. |
| `process-exit.txt` | `dumpsys activity` process‑exit records (16) | Shows CRASH_JAVA exits for the UI process and USER_REQUESTED stops for `:engine`. |
| `bug-report-template.txt` | Repro/issue template Arya prints | Tells the user to attach adb logs; not itself a bug. |
| `crash-buffer.txt` | Ring buffer of `AndroidRuntime FATAL EXCEPTION` stacks | The smoking gun for the JNI + FGS crashes. |
| `proc-snippets.txt` | `/proc/cpuinfo`, `getprop`, cpufreq | Confirms the big‑LITTLE Kirin topology and EMUI settings. |
| `app-logcat.txt` | Full logcat | The current build's daily life: it **never** crashes native, it keeps returning `prompt_exceeds_ctx`. |
| `app_logs/pokeclaw-app.log` | App‑side rolling log | `LocalLlmClient` retries, `TaskOrchestrator` errors. |
| `engine_logs/arya-engine.log` | `:engine` rolling log | Shows model loads succeeded and every `generateStream` died with `prompt_exceeds_ctx`. |
| `engine_logs/native-load-stage.txt` | Native "breadcrumb" trace (append) | The exact lifecycle and the failing stage. |
| `engine_logs/native-load-stage.prev.txt` | Previous rotation of the above (439 lines) | Shows a **prefill‑per‑token** run making slow progress (~70 ms/token) — evidence of the 1‑token Kirin workaround. |
| `engine_logs/native-heartbeat.txt` | Last native heartbeat line | The engine's last breath, at `prompt_toks_...`. |
| `engine_logs/native-env.txt` | Native env dump | Proves `n_ctx=1024`, `n_threads=1`, mmap, and the model loaded from the internal `files/models/fast` copy. |
| `engine_logs/native-maps.txt` | `/proc/self/maps` snapshot | Shown above the model is mapped from the APK/odex; no GPU buffers (CPU‑only). |
| `engine_logs/llama-cpp.log` | llama.cpp logging | Llama itself is healthy; no load/alloc error. |

## 2. The three real bugs (in order of impact)

### BUG 1 — every message fails with `prompt_exceeds_ctx` (this is why "it doesn't work at all")

Evidence:

* `native-env.txt`: `n_ctx=1024`, `rss_kb=109984`, and the model loaded from
  `/data/user/0/io.agents.arya/files/models/fast/google_functiongemma-270m-it-Q4_K_M.gguf`.
* `arya-engine.log`: every `nativeLoadModel … ok` shows `"ctx":1024`, then
  `generateStream native done … stats={"error": "prompt_exceeds_ctx"}`.
* `native-load-stage.txt` shows the tokenizer output: `tokenize_done_n_1246`, `n_1257`, and for the
  full agent prompt `n_4641`. **The prompt is always bigger than 1024 tokens.**
* `pokeclaw-app.log`: `LocalLlmClient generate failed … Engine process crashed or native error: prompt_exceeds_ctx`,
  `TaskOrchestrator onError …`, `FloatingCircle setState: ERROR`.

Why:

* The `MemoryBudget` planner **chose `1024` every time `available RAM < 6 GB`** (this device has ~4.6 GB free).
* The FunctionGemma prompt (short system + **9 tools**) tokenises to **~1.2k tokens**; the full agent prompt
  (**29 tools**, 21,316 chars) tokenises to **~4.6k**. Both are > 1024.
* The native code at `engine_jni.cpp` does `if (n_prompt >= n_ctx) return {"error":"prompt_exceeds_ctx"}`.
  So **generation never produces a single token**.

**Fix (applied):** three cooperating changes.

1. `MemoryBudget.plan` now takes `minCtxSize` (default **2048**) and **never silently picks a window
   smaller than the caller needs**. It picks the largest context that both fits RAM and ≥ the minimum,
   capped at 2048 (safe against the model's trained context and the KV‑cache/OOM problem that killed the
   1.7B engine). It refuses with an explicit message instead of loading 1024 and failing every generate.
2. `EngineCore.ensureLoaded` forwards the caller's `ctxSize` into the planner as `minCtxSize`.
3. New `LocalPromptBudget` in `LocalLlmClient`:
   * requests the window sized from the *actual* prompt;
   * trims **oldest** history turns (but **never the latest user message**), then shrinks the tool list
     to a focused on‑device set (12 → down to 3), and as a last resort truncates an oversized message
     (never removes it) — so the prompt can never overflow the loaded window.

The combined result on this device: the engine loads `ctx=2048`, the 9‑tool prompt (~1.2k tokens) fits
without any trimming, and the 29‑tool agent prompt is trimmed to a workable, shorter prompt and produces
output instead of an error.

### BUG 2 — the UI process repeatedly crashes with `ForegroundServiceDidNotStartInTimeException`

Evidence in `crash-buffer.txt` / `app-logcat.txt` (four occurrences, 13:42–13:46):

```
java.lang.NoSuchMethodError ... (see Bug 3)
android.app.ForegroundServiceDidNotStartInTimeException:
  Context.startForegroundService() did not then call Service.startForeground():
  ServiceRecord{... u0 io.agents.arya/.service.ForegroundService}
```

Why: `ForegroundService.onCreate` ran some setup **before** posting the foreground notification, and its old
code called `stopSelf()` *without* calling `startForeground()` when notification permission was missing
(and on Android 12 the 5‑second countdown can be missed on a cold/under‑memory start). Android 12 then
kills the process with this exception.

**Fix (applied):** `ForegroundService` now creates the channel and calls `startForeground()` **unconditionally
and immediately** in `onCreate`/`onStartCommand` via a `goForeground()` helper that never throws, treats a
missing `POST_NOTIFICATIONS` as only *hiding* the notification (not a reason to skip `startForeground`),
falls back to `startService()` if Android rejects a background‑sourced `startForegroundService`, and uses
`ServiceCompat.startForeground` with the declared `specialUse` type (correct on Android 14+ too).
`EngineService` (the `:engine` process) got the same treatment — its `startForeground` was moved to the top
of `onCreate`, ahead of `EngineCore`/native init which is what could blow the 5‑second window.

### BUG 3 — JNI callback `NoSuchMethodError` (`onDeltaPiece`/`onProgress`)

Evidence in `crash-buffer.txt`:

```
java.lang.NoSuchMethodError: no non-static method "Lye;.onDeltaPiece(Ljava/lang/String;)V"
  at io.agents.arya.engine.EngineNative.nativeGenerateStream(Native Method)
java.lang.NoSuchMethodError: no non-static method "Lcf;.onProgress(ILjava/lang/String;)V"
  at io.agents.arya.engine.EngineNative.nativeLoadModel(Native Method)
```

Why: the native code looked the Java callback method up **by name/type on the runtime object's class**.
After R8 obfuscation (`Lye;`, `Lcf;` are mangled class names) the slot no longer matched, so
`CallVoidMethod`/`GetMethodID` threw `NoSuchMethodError` and killed the `:engine` process.

**Fix (applied):**
* `engine_jni.cpp` now resolves `onDeltaPiece` against the **kept interface**
  `io/agents/arya/engine/EngineNative$NativeStreamCallback` via a cached global class ref, and only calls it
  if that lookup succeeded — it already degraded gracefully (continued without streaming) rather than crashing.
* `proguard-rules.pro` now explicitly keeps `EngineNative`, `NativeStreamCallback`, `NativeLoadCallback`
  and `StreamBridge` (and `native <methods>` entry points). `NativeLoadCallback`/`NativeStreamCallback`/
  `StreamBridge` are also already `@androidx.annotation.Keep` in `EngineNative.kt`.

The `onProgress` path is dead in the current loader (the loader no longer re‑enters Java — it passes `null`
progress), so that earlier crash can't recur; the keep rules are belt‑and‑suspenders.

## 3. Line‑by‑line highlights of the interesting files

### `summary.txt`
* `LAST ENGINE DEATH` → shows the heartbeat at `stage=prompt_toks_2_105_...` and `crash: (missing native-crash.txt)`.
  The native crash file being absent is the giveaway that **the engine did not crash** — it *returned* the
  `prompt_exceeds_ctx` error (the summary writer saw the recent heartbeat and assumed death).
* `Defaults`: `model=CPU-only llama.cpp`, `Local backend device: cpu`, `CPU-safe: Enabled`.
* `Local model storage`: internal and external model dirs both `availableBytes=59513819136` (~55 GB);
  external path is the FUSE‑backed `/storage/emulated/0/.../models/...`.
* `RAM: 12 GB total, 4.6 GB at report`, `memoryClass 384 MB`, `largeMemoryClass 512 MB`. This is why the
  old planner capped the context.

### `native-env.txt`
```
model_path=/data/user/0/io.agents.arya/files/models/fast/google_functiongemma-270m-it-Q4_K_M.gguf
n_ctx=1024 n_threads_arg=2 forced_threads=1 n_batch=1 n_ubatch=1 load_mode=MMAP+prefetch
compiled_arm_feature_dotprod=0
hwcap2_i8mm=1
ram_avail_mb=415 rss_kb=109984
llama_system_info=CPU : NEON = 1 | ARM_FMA = 1 | LLAMAFILE = 1 | REPACK = 1
```
This is the definitive proof of `n_ctx=1024`. Note `ram_avail_mb=415` — the fuse copy was avoided, it reads
the ext4 "fast" copy. `dotprod=0` means it was compiled without the dot‑product extension to dodge a SIGILL
on Kirin (matches the `1.2.16` commit).

### `native-load-stage.txt` (current run)
```
... model_load_begin → weights_pct_100 → model_load_return → prefetch_done → weights_loaded
... context_init_begin → context_init_return → warmup_begin → warmup_ok_0_rc_0_ms_29_cpu_7 → warmup_done
... complete
... generate_enter → tokenize_full_bos → tokenize_done_n_1173 → prompt_toks_... (then n_1184, n_1198, n_1246, n_1257)
```
Load works (the model fits),`warmup_ok` — only **generate** can't run because the prompt exceeds `n_ctx`.
The `prompt_toks_2_105_55060_...` line is the first ~12 prompt token ids the engine writes as a breadcrumb.

### `native-load-stage.prev.txt`
Shows the older run that **did** enter prefill, one token at a time:
```
prefill_in_0_of_413_tok_151644 → prefill_ok_0_rc_0_ms_71_cpu_7 → prefill_in_1_of_413 ... (≈70 ms/token)
```
That's the "one token at a time" prefill workaround for Kirin (n_ubatch=1). It made progress but was very slow —
another reason they later let the client trim the prompt rather than prefill thousands of tokens.

### `arya-engine.log`
```
EngineCore generateStream begin id=... promptChars=5601 mode=full maxTokens=192 ...
EngineCore generateStream native done id=... ms=21 stats={"error": "prompt_exceeds_ctx"}
```
`ms=21` — it bails out **immediately** because `n_prompt >= n_ctx`. Chronologically the last few show the user
typing `What is this shit` with `promptChars=21316 tools=29` → still `prompt_exceeds_ctx`.

### `crash-buffer.txt` / `app-logcat.txt`
The `NoSuchMethodError` and `ForegroundServiceDidNotStartInTimeException` stacks (Bugs 2 & 3).

### `process-exit.txt`
* `exit[3]`, `exit[13]` = `io.agents.arya:engine` stopped by the app (reinstall/clear‑data), **not** crashed.
* `exit[5..8]` = `io.agents.arya` `CRASH_JAVA` — matching the four FGS crashes.

|------|--------|
| `app/src/main/java/io/agents/arya/engine/budget/MemoryBudget.kt` | `minCtxSize` input; adaptive candidate ladder that never picks below the caller's needed window and caps at 2048; refuses clearly instead of loading too small. |
| `app/src/main/java/io/agents/arya/engine/EngineCore.kt` | Forwards the caller's `ctxSize` into the planner as the `minCtxSize` floor. |
| `app/src/main/java/io/agents/arya/agent/llm/LocalLlmClient.kt` | Sizes the window from the actual prompt, requests it via `ensureLoaded(ctxSize=…)`, and adds `LocalPromptBudget` (trims old turns / tool list / oversized messages). Both fallback `ensureLoaded` calls now use the same window. |
| `app/src/main/java/io/agents/arya/service/ForegroundService.kt` | Immediate, unconditional `startForeground` + `ServiceCompat` type handling + background‑start fallback. |

## 5. Remaining production‑readiness items (recommended, not blockers)

* The **29‑tool** full‑agent prompt is inherently too large for a 270 M on‑device model. For publishable
  quality, curate the on‑device tool list per task (or route heavy tasks to a cloud model) rather than
  shipping all 29 tools to a 270 M model. `LocalPromptBudget` currently keeps at most 12 and trims to fit —
  functional, but a focused tool set is better.
* `targetSdk 36` + `specialUse` foreground service type must pass Play policy; make sure your app‑store
  justification is filed (the manifest already declares the permission).
* I could **not** compile/run the Android build in this sandbox (no Android SDK/NDK, no Gradle offline, no
  emulator), so these edits are reviewed by hand and should be verified by a CI build + a smoke test on a
  12 GB Huawei before shipping.
* The planner now refuses (rather than silently loads 1024) on devices that genuinely can't fit 2048. That
  is intentional, but do message it in the UI so low‑RAM users know to free memory or use a cloud model.
